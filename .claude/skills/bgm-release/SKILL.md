# BGMリリース（公開ワークフロー）

Sunoで作ったBGMを「配布できる状態」まで持っていく公開側のスキル。作曲・作詞は `suno-music-production` の担当で、このスキルは**完成した音源・動画を劣化させずに世に出す**ことに責任を持つ。

第1作『放課後トークルーム』（2026-08-06完走）の実測がベース。リポジトリ **manabi-ai-lab/manabi-bgm** が生きた実例で、詳細手順は同リポジトリの `docs/`（PLAYBOOK・RESTORE・RELEASE・YOUTUBE）にある。**まずリポジトリの STATUS.md を読んで現在地を把握してから動く。**

## 最重要原則：画質・音質を守る

このワークフローの一番の敵は「善意の再エンコード」。容量を小さくしたい、形式を揃えたい、という理由で変換した瞬間に原本が失われる。

- **原本の判定は常に SHA-256**。ファイル名やサイズ感で判断しない。期待値は `tracks/<slug>/CHECKSUMS.md` に置く
- 書き出しは1回だけ。以降のコピー・分割・結合・リネームはすべて**バイト列を変えない操作**に限る
- スマホ受け渡しは「圧縮」ではなく「分割」で行う（`scripts/split-for-backup.sh`）。圧縮版を作った場合はファイル名に `_スマホ版` を入れ、配布物には絶対に使わない
- ハッシュ照合は**3か所**で行う：復元直後／Releaseアップロード後の再ダウンロード／別環境での取得時

## 役割分担（4者体制）

| 担当 | 役割 | 備考 |
| --- | --- | --- |
| あっきー | 最終判断・ログインが要る操作全部（YouTube・Drive・リポジトリ作成） | パスワードは誰にも渡さない |
| Claude | 文書・記録・検証・ショートのレンダ・TikTok代行・リポジトリ運用 | このスキルの読者 |
| Codex（あっきーのPC） | Driveからの復元・照合・Release作成など**PCのネットワークが要る実作業** | リポジトリの `AGENTS.md` が標準指示。依頼文は `docs/PROMPT_CODEX.md` の2フェーズ形式で書く |
| ChatGPT | 制作情報の保持者。記録の穴埋めに使う | 回収は `docs/PROMPT_GPT.md` の形式で |

他AIへの依頼文は必ず「**確認できないことは『不明』と書く**」「**破壊的操作の前に停止して報告**」を含める。フェーズを分け、フェーズ間であっきーの確認を挟むと事故が減る。

## 実行環境の制約と迂回路（Claude Code リモート環境）

実測で判明している制約。ハマったら回避策を探す前にここを見る。

| できないこと | 迂回路 |
| --- | --- |
| Google Drive への接続（403） | 大きいファイルはCodex（PC）に任せる。小さいテキストはDrive連携（MCP）で読める |
| GitHub Releaseへのアセットアップロード | Codexに `gh release create` させる（`scripts/create-release.sh` が照合込み） |
| 任意ホストへの大容量アップロード | 公開リポジトリの**一時ブランチ**に置き、`https://cdn.jsdelivr.net/gh/<owner>/<repo>@<branch>/<file>` 経由で先方に取り込ませる。raw.githubusercontent は MIME が octet-stream になり動画として弾かれるので**必ずjsDelivr**を使う |
| リモートブランチの削除（403） | あっきーかCodexに1行頼む |
| org への新規リポジトリ作成（403） | あっきーがWebで作る（Public・READMEなし）。中身はClaudeがpush |

一方で**できる**こと：GitHub Releaseアセットのダウンロード（649MBでも可）、PyPI直通（ffmpegは `pip install imageio-ffmpeg`、日本語フォントは `japanize-matplotlib` の sdist から `ipaexg.ttf` を抽出）、TikTok投稿（HiggsField MCP）。

## 工程の全体像

順番と各工程のチェックリストは `manabi-bgm/docs/PLAYBOOK.md` が正本。要点だけ：

1. **記録の器を先に作る**：`templates/` から `tracks/<slug>/` 一式をコピー。Suno情報は生成したその場で書かせる（後から思い出せた試しがない）
2. **検品**：仕様・ハッシュ・5点再生（0:00／映像ループ周期／音声ループ周期／中間／終端）。チェック位置はループ周期から計算して決める
3. **退避**：分割バックアップをDriveへ。パーツごとのハッシュ一覧も一緒に置く
4. **Release**：タグ `v1.0.0-<slug>`。**アセット名はASCII**（GitHubは日本語ファイル名の非ASCII文字を削除して `_1._.mp4` のような残骸にする）。Releaseノートに「日本語名にリネームしてよい（ハッシュは変わらない）」と書く
5. **YouTube**：限定公開→検品→SEO版タイトルに直して公開。設定は 音楽／子ども向けでない／**合成コンテンツ:はい**／自動チャプター:オフ
6. **ショート＋TikTok**（下記）
7. **コピペ集**：投稿素材が複数ファイルに散ると使う側が迷子になる（第1作で実際に苦情が出た）。**実URLを埋めた作業順の `COPYPASTE.md`** を最後に必ず作る

## SEO（タイトル・タグ）

探す側は「明るい フリーBGM」「かわいい フリーBGM」「雑談配信 BGM」のような**形容詞＋フリーBGM**で検索する（実在リスナーの行動から確認済み）。

- タイトル型：`【フリーBGM】<曲名>｜<形容詞>会話・雑談配信・作業用BGM【<尺>】`。「フリーBGM」を先頭、形容詞をその直後に
- タグ・概要欄にも同じ形容詞群（明るいBGM／かわいいBGM／ゆるかわ／SHOWROOM／推し活）を織り込む
- 実在の個人名は公開コンテンツに出さない（oshikatsu-profile-reference のルール）

## 縦型ショートの作り方

設計原則は**ループ前提＋冒頭1〜2秒に問いかけフック**（歴史ソングショートで維持率130.9%の実測）。台本・投稿文の実例は `tracks/after-school-talk-room/SHORTS.md`。

レンダはClaudeが自分でやる。手順は `scripts/render_short.py`（このスキルに同梱）を使う：

1. 素材はRelease版の本編MP4（ハッシュ照合してから使う）。低画質版・別経路の素材は使わない
2. **尺は映像ループ周期の整数倍**にする（例：10.041667秒×3周=30.125秒）。こうするとショート自体がシームレスにループする
3. 1080×1920。ぼかし背景＋中央に本編、テロップはPillowでPNG生成（白文字＋ピンク縁取り、フォントはIPAexゴシック）
4. 音声は本編の頭から、末尾0.3秒フェード
5. **必ず全テロップ区間のフレームを抜いて目視検品**してから納品（SendUserFileであっきーへ）

## TikTok代行投稿

HiggsField MCP の `tiktok_*` ツールで直接投稿できる。手順：

1. `tiktok_accounts` で接続確認（error なら reconnect のURLをあっきーへ）
2. 動画をHiggsfieldへ：ローカルからのPUTはプロキシで塞がれるので、**一時ブランチ＋jsDelivr URL→`media_import_url`**（上の迂回路表）
3. `tiktok_prepare_publish` → `tiktok_publish`。いつもの設定：**公開／コメント・デュエット・ステッチON／AI生成開示ON（is_aigc:true）／追加音楽なし・原曲音量100%**（BGMの宣伝に別の曲を乗せない）／商用コンテンツ開示なし
4. キャプションは150字以内（要カウント）。本文＋ハッシュタグ8〜12個
5. `tiktok_publish_status` で PUBLISH_COMPLETE を確認 → SHORTS.md の記録欄に反映 → 一時ブランチの削除を依頼

## 投稿の順番

**本編公開 → ショート**。ショートは本編への導線なので、先が限定公開のうちに出すと迷子になる。TikTokだけはプロフィールリンク導線なので先行してよい。

## 完了の定義

「全部やった」ではなく記録で終わる：STATUS.md にログと**次の一歩**を書き、記録欄（YOUTUBE.md／SHORTS.md／CHECKSUMS.md）のURLと日付が埋まり、COPYPASTE.md が実URLで完結していること。
